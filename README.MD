# Polaris DigiTech Box Management Service

A Spring Boot REST API for managing boxes, loading items, tracking
battery percentage, and controlling the box delivery/return lifecycle.

## Tech Stack

-   Java 25
-   Spring Boot 4.1.0
-   Spring WebMVC
-   Spring Data JDBC / `JdbcTemplate`
-   H2 Database
-   H2 Console
-   Spring Security
-   Spring Validation
-   Lombok
-   Maven

## Core Concepts

### Box ID / Transaction Reference (`txref`)

In this project, the **Box ID used by the API is the transaction
reference (`txref`)**.

The terms can therefore be understood as:

-   **Box ID** = the identifier used to identify a particular box in the
    API.
-   **Transaction reference (`txref`)** = that same identifier.
-   `txref` uniquely identifies the box throughout its loading,
    delivery, and return lifecycle.

For example, when creating a box:

``` http
POST /api/boxes
Content-Type: application/json
```

``` json
{
  "txref": "BOX001",
  "batteryPercentage": 80
}
```

`BOX001` is the box's identifier and transaction reference. Subsequent
API calls use that same value:

``` http
POST /api/boxes/BOX001/items
GET /api/boxes/BOX001/state
PUT /api/boxes/BOX001/battery
POST /api/boxes/BOX001/start-delivery
```

> Note: the database also has an internal numeric `id` generated by H2.
> That internal database ID is different from the externally used
> `txref`.

## Box States

A box moves through the following lifecycle:

``` text
IDLE
  |
  | load item
  v
LOADING
  |
  | finish loading
  v
LOADED
  |
  | start delivery
  v
DELIVERING
  |
  | complete delivery
  v
DELIVERED
  |
  | start return
  v
RETURNING
```

### State rules

-   A newly created box starts in `IDLE`.
-   Loading an item moves an `IDLE` box to `LOADING`.
-   A box remains `LOADING` until the explicit `finish-loading`
    operation is called.
-   `finish-loading` changes `LOADING` to `LOADED`.
-   `start-delivery` changes `LOADED` to `DELIVERING`.
-   `complete-delivery` changes `DELIVERING` to `DELIVERED`.
-   `start-return` changes `DELIVERED` to `RETURNING`.
-   Invalid state transitions are rejected.

The battery tracker does **not** automatically mark a box as `LOADED`
merely because the battery drops below 25%. The explicit final loading
operation remains responsible for completing loading.

# API Endpoints

Base URL:

``` text
http://localhost:8080
```

## 1. Create a Box

### Endpoint

``` http
POST /api/boxes
```

### Purpose

Creates a new box.

The supplied `txref` is the external **Box ID / Transaction Reference**
used by all subsequent API calls.

### Request body

``` json
{
  "txref": "BOX001",
  "batteryPercentage": 80
}
```

### Validation

-   `txref` is required.
-   `txref` must not exceed 20 characters.
-   Battery percentage must be between `0` and `100`.
-   `txref` must be unique.

### Example response

``` json
{
  "id": 1,
  "txref": "BOX001",
  "message": "Box created successfully"
}
```

------------------------------------------------------------------------

# 2. Load an Item

### Endpoint

``` http
POST /api/boxes/{txref}/items
```

### Purpose

Loads an item into a box.

The operation is transactional and uses a database row lock
(`SELECT ... FOR UPDATE`) to prevent concurrent loading operations from
calculating capacity from stale weight values.

### Example

``` http
POST /api/boxes/BOX001/items
Content-Type: application/json
```

### Request body

``` json
{
  "name": "PHONE_001",
  "weight": 100,
  "code": "PHONE_001"
}
```

### Validation

-   `name` is required.
-   `name` may contain letters, numbers, hyphen and underscore.
-   `weight` must be greater than `0`.
-   `code` is required.
-   `code` may contain uppercase letters, numbers and underscore.
-   The box must be in `IDLE` or `LOADING`.
-   Battery must be at least `25%`.
-   The item must fit within the configured maximum box capacity.

### State change

If the box is:

``` text
IDLE
```

after the first successful item load it becomes:

``` text
LOADING
```

Further items can be loaded while it is `LOADING`.

------------------------------------------------------------------------

# 3. Finish Loading

### Endpoint

``` http
POST /api/boxes/{txref}/finish-loading
```

### Purpose

Marks the loading operation as complete.

This is the explicit **final loading operation**.

### State change

``` text
LOADING -> LOADED
```

### Example

``` http
POST /api/boxes/BOX001/finish-loading
```

### Response

``` json
{
  "message": "Loading completed"
}
```

A box cannot start delivery until this operation has been successfully
completed.

# 9. Update Battery Percentage

### Endpoint

``` http
PUT /api/boxes/{txref}/battery
```

### Purpose

Updates the battery percentage reported by an external tracker/device.

A tracker can call this endpoint repeatedly as the battery level
changes.

### Request body

``` json
{
  "batteryPercentage": 30
}
```

Later, it can report:

``` json
{
  "batteryPercentage": 24
}
```

### Validation

Battery percentage must be between:

``` text
0 and 100
```

### Example response

``` json
{
  "txref": "BOX001",
  "batteryPercentage": 30,
  "message": "Battery updated successfully"
}
```

### Low battery rule

The minimum battery level for loading operations is:

``` text
25%
```

A battery report below 25% does not by itself mean that loading is
complete. The box remains in its current valid state; loading must still
be explicitly completed with:

``` http
POST /api/boxes/{txref}/finish-loading
```

# Capacity Management

The maximum box capacity is configurable and is not hardcoded in the
loading logic.

The application uses:

``` properties
box.max-weight=${BOX_MAX_WEIGHT:500}
```

Therefore:

-   Default maximum = `500g`
-   Environment variable = `BOX_MAX_WEIGHT`
-   The environment variable overrides the default.

Example:

``` bash
BOX_MAX_WEIGHT=700 mvn spring-boot:run
```

The application will then use a maximum capacity of `700g`.

## Capacity error

If a box has:

``` text
Current weight: 450g
Maximum capacity: 500g
```

then only:

``` text
50g
```

remains available.

If a user attempts to load a `100g` item, the API returns the remaining
capacity so the caller knows how much can still be loaded.

Example:

``` json
{
  "error": "Item exceeds box capacity",
  "currentWeight": 450,
  "itemWeight": 100,
  "maximumCapacity": 500,
  "remainingCapacity": 50
}
```

# Transactions and Concurrency

Item loading is handled inside a database transaction.

The loading operation performs:

``` text
BEGIN TRANSACTION
       |
       v
Lock box row
       |
       v
Read current weight
       |
       v
Validate battery
       |
       v
Validate box state
       |
       v
Validate capacity
       |
       v
Insert item
       |
       v
Update box weight
       |
       v
Update state if necessary
       |
       v
COMMIT
```

If an operation fails, the transaction is rolled back.

The box row is locked using:

``` sql
SELECT ...
FROM boxes
WHERE txref = ?
FOR UPDATE
```

This prevents concurrent loading requests from both reading the same
stale box weight.

# Database

The application uses an H2 in-memory database by default:

``` text
jdbc:h2:mem:boxdb
```

The database schema is defined in:

``` text
src/main/resources/schema.sql
```

Spring Boot runs the SQL initialization automatically using:

``` properties
spring.sql.init.mode=always
```

The main tables are:

### `boxes`

Stores:

-   Internal database ID
-   Transaction reference / external Box ID
-   Current weight
-   Battery percentage
-   Current state

### `items`

Stores:

-   Item ID
-   Item name
-   Item weight
-   Item code
-   Associated box ID

# Security

Spring Security is included in the project.

For the current assessment implementation:

-   `/api/**` is permitted so the API can be exercised.
-   `/h2-console/**` is permitted for development.
-   H2 console frames are allowed from the same origin.
-   CSRF is ignored for `/api/**`.

Authentication/authorization beyond this is not introduced unless
required by the assessment.

# Project Design Summary

The application separates responsibilities into:

``` text
Controller
   |
   v
Service
   |
   v
Repository
   |
   v
H2 Database
```

### Controller

Handles:

-   HTTP endpoints
-   Path variables
-   Request bodies
-   Request validation

### Service

Handles:

-   Business rules
-   State transitions
-   Capacity validation
-   Battery rules
-   Transactions

### Repository

Handles:

-   SQL
-   `JdbcTemplate`
-   Row locking
-   Database reads/writes

### Database

Persists:

-   Boxes
-   Items
-   Box state
-   Weight
-   Battery percentage
